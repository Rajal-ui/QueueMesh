# AWS Inspect Guide for QueueMesh Project

Make sure you are logged into the AWS Console and your region selector in the top-right corner is set to **N. Virginia (`us-east-1`)**.

Here is your step-by-step tour to inspect every component of QueueMesh across AWS services.

---

### 1. CloudFormation — The Infrastructure Stack

This is your single source of truth that proves all resources were deployed cleanly.

1. In the top search bar, type **CloudFormation** and open it.
2. Click on the **QueueMesh** stack name.
3. Select the **Resources** tab.
4. **What you are seeing:**
* A full inventory of every AWS resource created by your SAM template (`DynamoDB Table`, `SQS Queue`, `Worker Lambda`, `Controller Lambda`, and `IAM Roles`).
* Status should say `CREATE_COMPLETE` or `UPDATE_COMPLETE` for all rows.



---

### 2. AWS Lambda — Event Source Mapping & Scaling Limits

This is where the magic happens—where QueueMesh dynamically adjusts the concurrency limit of your worker.

1. Open **Lambda** from the top search bar.
2. Click on **`QueueMesh-Worker-dev`**.
3. Under the **Function overview** section, look at the **Triggers** box on the left.
4. Click on the **SQS: QueueMesh-TargetQueue-dev** trigger row.
5. Scroll down to the **Configuration** -> **Triggers** detail pane below.
6. Look for **Maximum Concurrency** (or **Scaling Configuration**).
7. **What you are seeing:**
* The live number (e.g., `100`, `50`, `25`, or `15`).
* When you invoke `QueueMesh-Controller-dev` via your CLI during the demo, refresh this page—you will see this exact number change live in the AWS UI!


8. Go back to Functions and click on **`QueueMesh-Controller-dev`**:
* Click **Configuration** -> **Environment variables**.
* Verify variables like `TABLE_NAME` (`QueueMeshStateLedger-dev`) and `TARGET_ESM_UUID`.



---

### 3. DynamoDB — The Brain & Audit Ledger

This is your state machine tracking active states and history.

1. Search for **DynamoDB** and select **Tables** from the left sidebar.
2. Click on **`QueueMeshStateLedger-dev`**.
3. Click the **Explore table items** button in the top right.
4. Look at the items returned in the table:
* **`SK = STATE#CURRENT`**: Look at attributes like `CurrentState` (`THROTTLED` or `RECOVERING`), `CurrentMaxConcurrency`, and `ConsecutiveBreaches`.
* **`SK = AUDIT#2026-09-20...`**: Each time QueueMesh evaluates a breach or recovery, it logs an immutable record with `action`, `previous_concurrency`, `target_concurrency`, and `execution_time_ms`.



---

### 4. Amazon SQS — The Target Event Queue

This is where inbound messages wait for processing.

1. Search for **SQS** (Simple Queue Service).
2. Click on **`QueueMesh-TargetQueue-dev`**.
3. Scroll down to the **Lambda triggers** tab.
4. **What you are seeing:**
* You will see `QueueMesh-Worker-dev` listed as the consumer with the active batch size and trigger status set to **Enabled**.



---

### 5. CloudWatch Logs — Telemetry Proof

This shows the raw telemetry generated by the worker and the controller execution logs.

1. Search for **CloudWatch** and select **Log groups** under **Logs** in the left sidebar.
2. Open `/aws/lambda/QueueMesh-Worker-dev`:
* Click on the latest log stream.
* You will see formatted JSON log entries containing `_aws` and `CloudWatchMetrics` (`Downstream200Count`, `Downstream429Count`). This proves you are emitting CloudWatch Embedded Metric Format (EMF) data.


3. Open `/aws/lambda/QueueMesh-Controller-dev`:
* Click the latest log stream.
* You will see the Boto3 execution logs showing the AIMD calculation and the successful call to `update_event_source_mapping`.



---
